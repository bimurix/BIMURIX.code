# Revue de sécurité et de conformité Loi 25 (T5) — 2026-11-13

Portée : site Bimurix **en local** (pile Supabase `bimurix`, dataset Sanity `development`, build de production sur le port 3200). Rien n'a été configuré en ligne. Méthode : chaque risque est prouvé par un test avant d'être corrigé. Les tests sont dans `web/tests/unit/` (`db-security.test.ts` contre la base locale, `quote-abuse.test.ts`, `proxy-internal-header.test.ts`).

Autres vérifications, sans constat :

- **Témoins de session `/admin`** : par défaut HttpOnly était faux. Corrigé : HttpOnly, SameSite=Lax, Secure en production (`lib/supabase/cookie-options.ts`, test).
- **Clé `service_role` / secrets dans le navigateur** : les valeurs de `SUPABASE_SECRET_KEY`, `IP_HASH_SALT` et `TURNSTILE_SECRET_KEY` ont été cherchées dans les 235 fichiers de `.next/static` du build : aucune occurrence.
- **RLS** : toutes les tables de `public` (4 avec `admin_login_attempts`) ont RLS ; `anon` n'a aucun droit de table ni d'exécution de fonction (test).
- **Pages `/admin`** : `Cache-Control: private, no-store` relevé sur le build ; chaque action serveur appelle `requireAdmin()` ; retour du lien magique fixe vers `/admin` (pas de paramètre de redirection) ; contrôle d'origine des actions serveur : celui de Next.js (même origine).
- **Injection dans les courriels** : transport par API JSON (pas d'en-têtes SMTP à injecter), objets réduits à une ligne (`oneLine`), HTML échappé, courriel validé.
- **Redirection ouverte, cache, déni de service** : `safeRedirectTarget` (tests existants) ; table des adresses lue au plus une fois par minute par instance ; copie du 404 gardée 5 min.
- **Journaux** : plus aucun message brut d'erreur dans les `console.error` de `lib/quote`, `lib/admin`, `app/admin`, `proxy` et de la table des adresses. Reste `sanity/fetch.ts` (hors de ma portée, ne manipule aucun renseignement personnel).

## 3. Loi 25

- **Consentement** : horodaté (`consent_at`) avec la version de la politique (`consent_policy_version`) ; désormais obligatoire.
- **Conservation** : anonymisation automatique à 24 mois après le dernier échange (pg_cron, 03 h 15), IP à 30 jours (03 h 30), tentatives de connexion à 1 jour (03 h 45). Trois tâches vérifiées actives dans la base locale.
- **Pages légales** : texte complet FR et EN dans `web/scripts/seed/legal.mts`, appliqué au dataset `development` par `scripts/patch-legal-t5.mts` (refuse tout autre dataset). Il nomme les cinq fournisseurs, le retrait du consentement, la plainte à la Commission d'accès à l'information, les durées, les courriels de notification (S-23). La ligne « à valider par un conseiller juridique avant la mise en ligne » est en tête de chaque page. Restent marqués « (exemple) » : raison sociale et NEQ, lieux de traitement des fournisseurs, durée des journaux de l'hébergeur, date de mise à jour (`check:placeholders` les signale).

### Procédure du fondateur (à garder hors du dépôt)

1. **Demande d'accès, de rectification ou de retrait du consentement** : répondre dans les **30 jours** ; retrouver la demande dans `/admin` par la référence ou le courriel.
2. **Suppression** : dans `/admin`, fiche de la demande, bouton **Anonymiser** (irréversible, journalisé). Ensuite, **supprimer à la main** les courriels de notification et les réponses dans la boîte `contact@bimurix.com` (la base ne les contrôle pas).
3. **Chaque trimestre** : vider de la boîte les notifications de plus de 24 mois ; vérifier que les tâches pg_cron tournent (`select jobname, active from cron.job`).
4. **Incident de confidentialité** : noter dans le registre, évaluer le risque de préjudice sérieux, aviser la CAI et les personnes concernées si oui.

## 4. Réglages à faire au déploiement (rien n'est fait en ligne)

**Supabase (projet en ligne)** : région Canada (Montréal) ; appliquer les 7 migrations ; activer l'extension `pg_cron` ; **fermer les inscriptions** (Authentication → désactiver « Allow new users to sign up ») ; liste des adresses de retour **exacte** (`https://bimurix.com/admin/auth/callback`, rien d'autre) et `site_url` ; durée du lien à 600 s ; valider « Enable email OTP expiry » ; limite d'envoi de courriels d'authentification ; SMTP personnalisé (Resend) pour les liens ; créer l'administrateur avec `pnpm admin:add` ; sauvegardes ; revoir les conseillers de sécurité Supabase (anciens 0028 et 0029 déjà traités).
**Netlify** : variables `NEXT_PUBLIC_SITE_URL`, `IP_HASH_SALT` (valeur longue et aléatoire, **obligatoire** : sinon alerte dans les journaux), `NEXT_PUBLIC_SUPABASE_URL`, clé publique, `SUPABASE_SECRET_KEY`, `TURNSTILE_SECRET_KEY` **réelle**, `MAIL_TRANSPORT=resend`, `RESEND_API_KEY`, jeton Sanity en lecture ; **ne pas** définir `NEXT_PUBLIC_SITE_URL` sur les aperçus de déploiement avec le domaine final ; HTTPS forcé ; durée de conservation des journaux (à confirmer pour la politique).
**Cloudflare Turnstile** : créer le widget pour `bimurix.com`, clé de site et clé secrète réelles (les clés de test sont refusées en ligne).
**Resend** : vérifier le domaine (SPF, DKIM, DMARC), adresse d'envoi `contact@bimurix.com`.
**Sanity** : limiter les origines CORS à `bimurix.com` ; revoir les comptes ayant accès à Studio ; authentification à deux facteurs ; dataset `production` seulement à la phase M.
**Boîte courriel du fondateur** : validation en deux étapes (un seul facteur protège `/admin`).
**Texte légal** : faire valider par un conseiller juridique, remplacer les valeurs « (exemple) », puis retirer la date d'exemple.
