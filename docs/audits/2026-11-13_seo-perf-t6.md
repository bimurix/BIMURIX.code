## 1. Test rouge `admin.spec.ts` / `magicLogin` (S-05)
- **Cause** : pas un défaut du code de T5. Hors Netlify l'IP n'est pas connue ; seule la limite globale (30 liens/heure) s'applique. La suite en consomme 5 par passage ; quelques relances l'atteignent et plus aucun lien n'arrive. Reproduit en insérant 30 lignes dans `admin_login_attempts` (test rouge), puis corrigé.
- **Correction** : le test vide le compteur de la base locale avant chaque connexion ; nouveau test « 30 liens dans l'heure, le suivant n'envoie rien » (la limite reste vérifiée). Code de `lib/admin/` inchangé. Commit `9f98b88`.
- Au passage : le lien de retour construit pour le port 3200 n'est pas dans la liste d'adresses de retour de Supabase (`config.toml` : port 3100 seulement) ; la connexion aboutit quand même via l'adresse du site (3100). À corriger en ajoutant 3200 à `additional_redirect_urls` si on veut un test 100 % sur 3200 (demande un redémarrage de Supabase : non fait).

## 2. S-07 / R-22 (`SanityLive`)
- Constat mesuré : le code réel de `SanityLive` (client Sanity, ≈ 13 Ko gzip) se charge **après l'hydratation**, donc hors du « JS initial » mesuré, et ouvre une connexion permanente vers Sanity pour chaque visiteur. Avec un jeton de lecture configuré, `browserToken` l'aurait envoyé à tous les visiteurs.
- Fait : `browserToken` retiré (le jeton reste côté serveur) ; `SanityLive` monté seulement en développement ou avec `NEXT_PUBLIC_SANITY_LIVE=1`. Le JS initial n'a **pas** baissé (le composant d'enveloppe reste dans un code partagé).
- **Non vérifié** : en production sans `SanityLive`, une modification de Studio doit apparaître d'elle-même au plus tard en 15 min (profil de cache `default` de Next). À confirmer en ligne ; à la phase M, brancher une revalidation à la publication (webhook Sanity) pour l'instantané.
