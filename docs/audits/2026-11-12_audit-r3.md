# Audit R3 — vérification finale après R1 et R2 (2026-11-12)

Audit indépendant : rien n'a été repris des rapports précédents. Cible : site local (port 3100), dataset Sanity
`development`, Supabase local. `production` n'a été **que lu** (requêtes de lecture publiques).

## Verdict
Le site est conforme à ADR-006 et ADR-007, sauf **un point de contenu à trancher par le client** (l'ancien texte de la page
« Préfabrication MEP », voir tableau). 3 défauts corrigés. Aucune erreur de sécurité trouvée.

## 1. Commandes (dans `web/`, après la dernière correction)
| Commande | Résultat |
|---|---|
| `pnpm lint` | 0 erreur |
| `pnpm typecheck` | 0 erreur |
| `pnpm test` | 10 fichiers, **92 tests** passés |

| `PLAYWRIGHT_PROD=1 pnpm test:e2e` (build de production, référence) | **129 réussis, 3 échecs, 8 ignorés** : les 3 échecs sont deux vrais défauts du mode production (§ 10) |

Tests instables trouvés au premier passage (128 passés, 2 échecs) : le changement de langue (`pages.spec.ts`) et la fiche
admin (`admin.spec.ts`). **Cause** : en mode dev, chaque route est compilée à sa première visite ; l'adresse EN de
destination, `/admin/auth/callback` et la fiche `/admin/demandes/[id]` n'étaient pas préchauffées, et sous 6 travailleurs
la compilation dépassait les délais. Correction : préchauffage complété (`warm-up.ts`), délais élargis là où la route est
protégée donc non préchauffable. Les passages suivants ont montré le même défaut sur d'autres étapes (lien magique, statut, note de la fiche admin :
choix fait avant l'hydratation, action serveur compilée au premier appel) : délais élargis et gestes refaits jusqu'à
réussite. Cause de fond : le serveur de dev laissé ouvert occupait 3 Go (redémarré) et compile chaque route à la demande ;
**un test qui ne flanche qu'en suite complète sous `next dev` est une instabilité du mode dev, non un défaut du site**.
Pour une référence stable, `PLAYWRIGHT_PROD=1` lance la suite contre le build de production (`node scripts/next-dev-env.mjs build`
puis la suite ; 2,7 min au lieu de 5 à 7). Dernière instabilité dev vue : « le lien de langue mène à l'autre version » (mobile,
15 s dépassées sous charge), réussi contre le build de production.

## 10. Défauts du mode production trouvés (corrigés le 2026-11-12, tâche S4 ; voir « Correction S4 » ci-dessous)
Seulement visibles contre le build de production (`next start`), invisibles en mode dev :
1. **Adresse inconnue : la toute première visite répond 200** (puis 404 aux visites suivantes, page « noindex » dans les deux cas). Le code veut un vrai 404 (`instant = false`), mais le rendu à la demande des adresses non pré-générées répond 200 avant de savoir que la page n'existe pas. Test : `pages.spec.ts:29`.
2. **Ancienne adresse « préfabrication MEP » : statut 308 sans en-tête `Location`** (la redirection se fait par script dans la page ; la première visite répond même 200). Les navigateurs avec JavaScript arrivent bien à la nouvelle page ; les robots et sans-script non. Test : `pages.spec.ts:61`.
Pistes (à décider avec un développeur, car elles changent la façon dont Studio publie) : redirections lues dans Sanity à la construction (`redirects()` de `next.config.ts`) ; `dynamicParams = false` pour un 404 immédiat (mais une adresse changée dans Studio exigerait alors une reconstruction). À vérifier aussi sur Netlify, dont le moteur d'exécution peut se comporter autrement.
Autre écart de mode : en production le formulaire de soumission n'apparaît qu'après le chargement du script (pas de formulaire inactif avant, donc pas de risque d'envoi en GET) ; le test « connexion lente » a été rendu valable pour les deux modes.

### Correction S4 (2026-11-12)
**Cause** : avec les composants en cache (`cacheComponents`), une page non pré-générée est envoyée en streaming : l'en-tête de réponse part (200) avant que la page découvre que l'adresse est inconnue (`notFound()`) ou déplacée (`redirect()` devient alors une redirection « par script » sans en-tête `Location`). `instant = false` n'y change rien, et un `rewrite` de proxy ne peut pas imposer un statut.
**Correction** : le statut est décidé *avant* le rendu, dans `src/proxy.ts`, à partir d'une table des adresses lue dans Sanity (`src/lib/route-table-source.ts` : pages et services visibles + documents « Redirection »), gardée 60 s en mémoire par instance (une requête Sanity par minute au plus, jamais bloquante une fois la table chargée). Règles pures et testées dans `src/lib/route-table.ts` (`tests/unit/route-table.test.ts`) :
- adresse connue ou accueil : rendu normal ; une page existante l'emporte sur une redirection de même adresse ;
- ancienne adresse : vrai **308** (307 si « temporaire » dans Studio) avec `Location`, via `safeRedirectTarget` (pas de domaine externe, pas de boucle) ;
- adresse inconnue (FR et EN) : **404** avec la page « introuvable » de Studio. Le proxy renvoie le gabarit pré-généré `/_404` (`/en/_404`), copié en mémoire 5 min, avec le statut 404 (`src/lib/not-found-response.ts`). Ce gabarit est lui-même servi en 404 aux visiteurs.
Aucune reconstruction : créer une page, changer une adresse ou ajouter une redirection dans Studio est pris en compte en moins d'une minute. Le code de la page garde sa propre redirection/404 en filet de sécurité. Sanity injoignable : le proxy ne tranche pas (comportement d'avant). `_404` est une adresse réservée.
**Preuves (build de production, port 3200, première visite)** : `/cette-page-n-existe-pas` 404, `/en/zzz` 404, `/_404` 404, `/services/prefabrication-mep` 308 → `/services/prefabrication-tuyauterie`, `/en/services/mep-prefabrication` 308 → `/en/services/piping-prefabrication`, `/a-propos` 200 ; dev (port 3100) inchangé : 404 et 308.
**À vérifier sur Netlify** : (1) que le proxy (Node) peut lire son propre site pour copier le gabarit 404 (sinon il se rabat sur la page « introuvable » rendue, qui répond 200 la première fois) ; (2) la mémoire d'une instance de fonction est courte : plus de requêtes Sanity possibles, sans conséquence fonctionnelle ; (3) le délai de 60 s pour une nouvelle page. Aucune configuration en ligne n'a été faite ; un webhook Sanity → reconstruction Netlify n'est pas nécessaire pour ces deux défauts.
Outils : `PLAYWRIGHT_BASE_URL=http://localhost:3200 PLAYWRIGHT_PROD=1 pnpm test:e2e` teste le build de production sur un autre port sans toucher au serveur de dev (`node scripts/next-dev-env.mjs start -p 3200`).
